## Decisions

- D1: one pass does parse, check and lower (syntax-directed translation); a first pass only collects subprogram signatures so calls may precede definitions (CIE-70).
- D2: `cie/` imports `Cursor`, `Abandon`, `joinSpans`, `Token` from `edexcel/`. Follow-up: move them to a shared folder.
- D3: CASE is desugared to an if-chain; OUTPUT lists to a `concatText` chain. No new IR nodes.
- D4: `statements.ts` is about 600 lines, over the 400 guide. Follow-up: split CASE, loops and element assignment out.
- D5 (arrays, #69 and this PR): two shared IR nodes, `newArray` and `copyArray`; everything else reuses `index` and `element` (`base` = declared lower bound, `growOnWrite: false`). DECLARE of an array lowers to an assignment of `newArray`, so a trace table shows the array at its DECLARE line.
- D6: a 2D array whose two dimensions start at different numbers, and arrays with 3+ dimensions, report `E-SYN-NOT-SUPPORTED` (one `base` per access). The spec says "any integer bounds" for 1D and shows only 1-based 2D, so this is a gap, not a contradiction.
- D7: wrong number of indexes reports `E-SYN-EXPECTED` ("one index" / "two indexes"); no new message code. Whole-array assignment of a different size or item type reports `E-CHK-TYPE-CHANGE`.
- D8: `INPUT A[i]` (CIE-80) needed `input.target` widened to `AssignTarget` in shared IR; done in its own small PR (the interpreter now routes input through `assign`), and the CIE-80 element golden passes.
- D9 (built-ins, CIE-120 to 129): a table in `cie/builtins.ts` gives each function's argument kinds and result type; each is its own shared `BuiltinName` (`left`, `numToStr`, `truncate`, ...) run by `runtime/builtins.ts`. A DATE is a new runtime value (`{kind:"date"}`), printed `dd/mm/yyyy`. The machine gained `randomReal()` and `today()`.
- D10: the spec says a wrong argument value is an error but gives no wording, so one new runtime code `E-RUN-BAD-ARGUMENT` covers: LEFT/RIGHT/MID asking for characters that are not there, STR_TO_NUM of non-numbers, ASC/CHR outside 0 to 127, RAND of a negative, SETDATE of a day that does not exist. Wording needs your check.
- D11: `STR_TO_NUM` is typed REAL (the text decides at run time; an INTEGER fits a REAL, not the reverse). See Q49.
- D12: DATE values cannot be compared yet, and the `dd/mm/yyyy` DATE literal of CIE-04 is not lexed yet (use SETDATE). Both are gaps, not decisions.
- D13 (records, CIE-30/48): shared IR gained `newRecord`, `field` (read) and a `field` assign target. Records are shared by reference like arrays; whole assignment lowers to `copyArray`, which now deep-copies records. A field line without DECLARE is accepted with warning `W-CIE-FIELD-DECLARE`. Records are not comparable (CIE-48).
- D14 (enums, CIE-31): values are declared as constants that lower to `enumValue`; order comparison lowers to INTEGER comparison of ordinals (`enumOrdinal`), so shared comparison code is untouched. `S + n` / `S - n` lower to `enumStep`; going past either end is `E-RUN-ENUM-RANGE`. The spec does not say what happens past an end; see the new question in QUESTIONS.md.
- D15 (BYREF, CIE-73/76): copy-in/copy-out. Shared IR: `Subprogram.byRef` and `callStatement.outs`; a procedure with BYREF parameters returns their final values and the caller writes them back (the `assign` path, so the trace table sees them). A BYREF argument must be a variable, array item or record field (`E-CHK-BYREF-ARG`). BYVAL record arguments are copied in (`copyArray`). BYREF in a FUNCTION only warns (CIE-75) and is passed by value; copy-out is not done for functions. Array parameters cannot be declared yet (no `ARRAY` in a parameter type): a gap.
- D16: names are case-insensitive (CIE-03): `Env` keys variables by lower-case name and keeps the first spelling; IR uses that spelling, so the trace table shows the declared name. A different casing gives `W-CIE-NAME-CASE`. CIE-11: an undeclared name is reported once, then declared with an unknown type so later uses stay quiet. CIE-45 is reported at the `&`. Subprogram names are still case-sensitive (gap).
- D17 (TRY, CIE-100/101): one shared IR node `tryCatch {body, handler}`; the interpreter catches `RunError` around the body (errors in called subprograms arrive through the driver's re-throw). Errors inside the handler are not caught. Step-limit and Stop are not `RunError`s inside the interpreter, so they cannot be caught. `FINALLY` is `E-SYN-NOT-SUPPORTED` at the word.
